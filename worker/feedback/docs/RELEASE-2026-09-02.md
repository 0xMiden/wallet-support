## 2. OAuth callback URI

Register this **exactly**, in Google Cloud Console → APIs & Services →
Credentials → your OAuth client → *Authorised redirect URIs*:


No trailing slash. Google matches the string literally; a mismatch fails at

## 3. The secret commands

Each of these **creates and deploys a new Worker version.** They are production
writes, not preparation. They redeploy the code that is *already* live with an
added binding — they do not ship the new application code.

```bash
cd ~/miden-feedback-v2

# 1. Session signing key. Any long random string; generate one:
#    openssl rand -hex 32
npx wrangler secret put ADMIN_SESSION_SECRET

# 2/3. From the OAuth client created in step 2 above.
npx wrangler secret put GOOGLE_OAUTH_CLIENT_ID
npx wrangler secret put GOOGLE_OAUTH_CLIENT_SECRET
```

**What each changes:** adds one secret binding to `miden-feedback-v2` and
deploys a version carrying it. Currently-deployed code reads none of these
names, so behaviour does not change — but the version count does, and a
rollback target moves.

Rotating `ADMIN_SESSION_SECRET` later invalidates every open session
immediately. That is the emergency "sign everybody out" lever.

## 4. Verify secret NAMES (never values)

```bash
npx wrangler secret list
```

Cloudflare never returns values; this prints names and types only. Expect
**nine** after step 3:

```
TURNSTILE_SECRET  INGEST_HMAC_KEY  BACKFILL_TOKEN  GITHUB_WRITE_TOKEN
LLM_API_KEY_PRIMARY  LLM_API_KEY_FALLBACK
ADMIN_SESSION_SECRET  GOOGLE_OAUTH_CLIENT_ID  GOOGLE_OAUTH_CLIENT_SECRET
```

### Two protections, not one

**Wrangler's own `secrets.required` check.** `wrangler.jsonc` declares every
secret this Worker needs. Cloudflare's current documentation and its March 2026
changelog describe three behaviours for that field:

- `wrangler dev` **warns** about missing required secrets
- `wrangler types` uses the declared names
- `wrangler deploy` and `wrangler versions upload` **fail** when any are missing

> The schema summary bundled with the pinned Wrangler (4.124.0) mentions only
> local-dev validation and type generation. Treat that summary as **incomplete
> rather than authoritative** — it does not mention the deploy-time failure the
> official documentation describes. **This has not been tested against the
> pinned version here**, and nothing in this repository should be read as
> claiming it was. See "Settling it empirically" below.

**`scripts/deploy.sh`'s remote preflight**, kept as defence in depth. Before
uploading anything it:

- checks the **exact canonical Worker** named in `wrangler.jsonc`, so it cannot
  be reassured by a different one
- asks Cloudflare which secrets that Worker actually has, and prints a clear
  list of any missing **names**
- **never reads or prints a value** — `wrangler secret list` returns names and
  types only, and nothing in the script echoes a secret
- keeps protecting the release if Wrangler's behaviour or its diagnostics
  change, which is the point of not relying on a single mechanism

`SKIP_SECRET_CHECK=1` exists for the genuine first deploy of a new Worker.

#### Settling it empirically

If the pinned version's deploy-time behaviour needs to be a fact rather than a
citation, the test is: create a **disposable** Worker, declare a dummy required
secret it does not have, and attempt a deploy.

**Do not test this by deleting or rotating a production secret.** That is a
production write with a real blast radius, to learn something about tooling.
Creating and deleting a scratch Worker is its own approval, separate from any
release step.

## 5. Release manifest

**Deployed baseline:** `bba641b3726e704fa985d1510ec1aca019ba3790` — *inferred,
not proven.* Cloudflare records `Source: Unknown` for every deployment this
Worker has had. The basis: the last deployment is stamped
`2026-08-27T10:05:33Z`, and `bba641b` was authored `2026-08-27 18:05 +08` =
`10:05 UTC` — seconds apart, with no later commit in existence. That guesswork
is what `--tag` removes for every future deploy.

### Compute the range; do not read a number from this file

A commit count written down here is wrong the moment anything else lands —
including the commit that writes it down. Derive it from the thing you are
actually deploying:

```bash
DEPLOYED_BASE=bba641b3726e704fa985d1510ec1aca019ba3790
RELEASE_CANDIDATE=$(git rev-parse HEAD)

git rev-list --count "$DEPLOYED_BASE..$RELEASE_CANDIDATE"
git log --oneline "$DEPLOYED_BASE..$RELEASE_CANDIDATE"
```

`RELEASE_CANDIDATE` must be **the exact commit being deployed, from a clean
working tree** — not "whatever `master` points at" when somebody happens to run
this later. `scripts/deploy.sh` refuses a dirty tree for the same reason: a
manifest describing a different tree than the one that shipped is worse than no
manifest, because it reads as authoritative.

## 6. Smoke test

Run in order. Stop at the first failure and roll back.

```bash
# 1. The right code is serving. Must match the SHA you deployed.
curl -s https://miden-feedback-v2.miden-feedback-relay.workers.dev/health | jq '{ok, commit}'

# 2. The feedback form still answers. This is the thing that must not break.
curl -s -o /dev/null -w '%{http_code}\n' https://miden-feedback-v2.miden-feedback-relay.workers.dev/
# expect 200

# 3. /submit still refuses an unverified request on its OWN terms,
#    NOT with a sign-in page.
curl -s -X POST https://miden-feedback-v2.miden-feedback-relay.workers.dev/submit | head -c 200
# expect a JSON error. If you see "Continue with Google", the gate has leaked
# onto the public form — roll back immediately.

# 4. The console is closed to strangers.
curl -s https://miden-feedback-v2.miden-feedback-relay.workers.dev/admin/review | grep -c "Continue with Google"
# expect 1

# 5. Script endpoints still use their token, not a browser session.
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "authorization: Bearer $BACKFILL_TOKEN" \
  https://miden-feedback-v2.miden-feedback-relay.workers.dev/admin/quarantined
# expect 200
```

**6. Then sign in yourself, in a browser.** This is the step no curl can
replace: `/admin/review` → Continue with Google → pick `ivan.l@miden.team` →
you should land in the queue. If it says *"the sign-in link did not match this
browser"*, the state cookie was withheld — roll back and tell me.

**7. Confirm the drain is still running.** Wait two minutes, then check that
`/health`'s `publish` counters are moving as normal and nothing has piled up in
`deferred`.

## 7. Rollback

**Fastest, no rebuild:**

```bash
npx wrangler deployments list          # find the version before this deploy
npx wrangler rollback [<version-id>]
```

This restores the previous code. The database is **not** rolled back — and does
not need to be. `0007`, `0008` and `0009` are all additive: older code does not
know those tables exist and never queries them.

**If sign-in is the problem specifically**, rollback is the answer, not a
config change. There is no kill switch for the gate on purpose: a switch that
disables authentication is a switch that can be flipped by accident.

**If you need everyone signed out right now** without a rollback:

```bash
npx wrangler secret put ADMIN_SESSION_SECRET    # a new random value
```

Every existing session cookie fails signature verification immediately. You
sign in again; nobody else can until you do.

**Do not** roll the database back. Dropping `admin_allowed` locks the console
for everyone while the new code is live; dropping `admin_oauth_state` makes
every sign-in attempt fail closed, which is the same outcome by a different
route.
